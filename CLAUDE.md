# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant Telegram AI sales-agent platform. The repo is split into **shared, tenant-agnostic core packages** (`core/`, `channels/`, `rag/`, `voice/`, `notifications/`, `sync/`, `db/`) and **tenants** under `apps/` that are pure configuration + wiring — a tenant declares its prompt, `@tool` functions, and channel bindings, then hands a `Tenant(id, agents, channels, sync_jobs)` to `Runtime`. Adding or changing a tenant should not require touching the core packages.

Four tenants ship today:

- `apps/oygul/` — flower shop: a customer userbot "Lola" + a merchant catalog bot.
- `apps/anfa/` — Tashkent clinic: a service-catalog advisor on bot+userbot. It searches the clinic's priced service catalog, quotes prices, and directs clients to walk into the clinic. There is **no online booking** — the clinic keeps its own local-only CRM and registers patients in person; it exports its service list as Excel, which the admin panel ingests into Postgres → Chroma.
- `apps/byd/` — BYD Medical detox clinic: a faithful rebuild of the clinic's Bitrix24 sales funnel. A customer userbot (AI sales agent) + an operator bot (manager agent + inline buttons) + a durable per-deal scheduler firing ~23 time-delayed touches across 8 stages, mirrored into Bitrix24 (`bitrix.py`/`bitrix_sync.py`), with a PDF booking voucher (`voucher.py`).
- `apps/maskan/` — Maskan grave care: an AI advisor on a client userbot that sells grave care end to end. **Standalone since 2026-08-20**: it owns its catalogue, cemeteries, graves and orders, and takes money through the operator's own Payme/Uzum merchant account — see "Maskan is standalone" below. It began as a front end for an existing Flutter app + Django/DRF backend (`app.mas-kan.uz`); that integration (`api_client.py`, `order_watcher.py`, `backend/botapi/`) is still in the tree but no longer wired.

Separately, two internal **admin panels** read/write the shared Postgres without being part of the tenant runtime: `admin/` + `web/` (FastAPI + React) and `django_admin/` (Django admin). See "Admin panel" and "Django admin panel" under cross-cutting patterns.

Python ≥3.12, managed with **uv**.

There is **no test suite and no configured linter/formatter** — don't go looking for `pytest`/`ruff` config. Verify changes by running the relevant entrypoint.

## Request lifecycle (the central flow)

Read these together — the flow spans `channels/telegram/_telethon_base.py`, `core/channel.py`, `core/agent.py`, and `core/context.py`:

1. A Telegram message arrives. `TelethonChannel` **debounces and batches** rapid messages per chat (`debounce_seconds`), transcribes voice via `voice/`, downloads photos, and builds multimodal user content (text + base64 image blocks). A picture sent **uncompressed ("send as file")** arrives as a *document*, not a photo — those are picked up too (`_is_image_file`, stickers/GIFs excluded), and the data-URL mime is sniffed from the magic bytes since a file keeps its original format. PDFs are still ignored.
2. `Channel.dispatch(chat_id, content)` **publishes three context vars** (`current_tenant_id`, `current_chat_id`, `current_channel`) and then calls `Agent.invoke()`, resetting them in a `finally`.
3. `Agent` wraps LangChain `create_agent` + a LangGraph checkpointer. Conversation state is keyed by `thread_id = "{tenant}:{channel}:{chat_id}"` (see `Channel.thread_id`).
4. **Tools read the live channel and chat from `core.context`**, not from their arguments — that's how `search_bouquets_tool` sends a photo album or a "typing…" status mid-call. When writing a new tool, pull `current_channel`/`current_chat_id` from `core.context`; never expect them as parameters.
5. The final assistant text is returned and the channel sends it.

`Runtime.run_async()` launches every channel and sync job as **independent asyncio tasks** — if one crashes (e.g. an unauthorized userbot session), the others keep running; a per-task watcher logs the failure. Shutdown is on SIGINT/SIGTERM.

## Cross-cutting patterns you must understand before editing

**AI-mute / human handoff.** When a customer pays (oygul) or requests an operator (anfa's `request_operator` tool), a tool calls `mute_store.mute(chat_id)` and notifies operators with an inline **"Подключить ИИ"** button. While a chat is muted, `Channel.dispatch()` returns `""` (no reply) and the channel stays *fully passive* — no read receipts, no typing/online presence — so the human operator silently owns the conversation. An operator clicking the button fires a Telethon `CallbackQuery` handler (registered via `channel.add_callback_handler` in the tenant entrypoint) that calls `unmute()`. **Critical:** the mute is *set* in one process (the customer userbot) but *cleared* in another (the merchant/bot process), so the `MuteStore` must be shared across processes.

**Persistence is Postgres-only — `DATABASE_URL` is required.** There is no JSON / in-memory fallback (it was removed). `PostgresMuteStore`/`PostgresTokenStore` (satisfying the `MuteStore`/`TokenStore` Protocols in `core/`) + `AsyncPostgresSaver` back every tenant process, shared and durable. Each tenant's `services.py` constructs the stores unconditionally; `db.checkpointer_scope()` — which every entrypoint wraps around `Runtime.run_async()` — raises `SystemExit` if `DATABASE_URL` is unset.
- **`db/` imports stay lazy** — sqlalchemy/psycopg are imported inside the functions/methods that use them (mirroring `rag`/`voice`), so importing `db` is cheap and startup doesn't pay for the DB drivers until a store/engine is first used. Keep new `db/` code lazy.
- `db/models.py` holds only shared, tenant-agnostic runtime state (`muted_chats`, `chat_token_usage` + the shared `Base`). Per-tenant **domain** data (catalogue, orders, …) lives in `apps/<tenant>/models.py` + `apps/<tenant>/repository.py` — see "Adding a tenant".

**Admin panel (`admin/` + `web/`).** A standalone FastAPI service (console script `admin-api`, pm2 app `admin-api`) that reads/writes the **same shared Postgres** the bots use — muted chats, per-chat token usage, and conversation checkpoints — and imports none of the agent/Telegram runtime. It **requires `DATABASE_URL`** (like the bots — it reads the same shared Postgres). Its deps live in the `admin` optional-extra (`uv sync --extra admin`), kept out of the base install so a bot-only deploy stays lean. The API is mounted under `/api`, and the **same process serves the built React UI** (`web/dist`, from `npm run build`) at `/` — so the whole panel is one pm2 app on one port (`admin-api`, default `127.0.0.1:8100`). (`npm run dev` + the `/api` Vite proxy gives hot-reload during development.) The tenants the panel knows about are a static registry in `admin/tenants.py` (`TENANTS`). The panel can also **view and edit each agent's system prompt** (a "Prompts" tab, gated by the `has_prompts` capability): the editable `.md` files are a static registry in `admin/prompts.py` — the client only ever sends a `(tenant, key)` pair and the file path is resolved server-side, so edits are bounded to those files (no client-supplied paths). This is the one place the panel writes outside Postgres: it writes the prompt files on disk directly. Every agent loads its prompt via a **callable that re-reads its file on each invoke**, so a saved edit goes live on the running bot without a restart (the `Agent` rebuilds its graph only when the rendered text changes; anfa's catalog prompt additionally substitutes `{now_iso}`/`{weekday}`). This relies on the bots and `admin-api` sharing the host filesystem — they do under pm2. The anfa panel also exposes an **Excel catalog upload** (`POST /api/tenants/anfa/catalog/import`, gated by `has_catalog_import`): it parses the clinic's export and reconciles the `anfa_catalog` Postgres table (the bot's KB sync mirrors it into Chroma on the next tick).

**`/clear` and `/reset`.** Handled in `_telethon_base.py`: these commands wipe the chat's conversation thread (`Agent.clear_thread`) **and** zero its token tally (`Agent.clear_tokens` → `TokenStore.reset`). `reset(chat_id)` is part of the `TokenStore` Protocol, implemented by `PostgresTokenStore`.

**Django admin panel (`django_admin/`).** A second panel over the *same* Postgres, independent of `admin/` — different process, different port (`8200`), different extra (`uv sync --extra panel`). Where the FastAPI panel is purpose-built (chats, usage, prompt editing, the anfa imports), this one is a CRM over every table: funnels, orders, price lists, graves, the corpus — plus the pages that decide who to talk to and what the funnel is about to send. What decides its shape:
- **Alembic stays the only schema owner.** Every model is `managed = False` and `crm/routers.py` returns `False` from `allow_migrate` for the whole app, so `manage.py migrate` cannot touch the shared database. Django's own tables (users, sessions, admin log) go to a local SQLite file (`DJANGO_PANEL_DB`) — which also means panel logins are per-host state, not shared with the bots.
- **Three tables can't be registered.** `muted_chats`, `chat_token_usage` and `chat_profiles` are keyed by `(tenant_id, chat_id)`, and Django's admin refuses composite primary keys. Using `chat_id` alone as a fake pk would be a real bug — the same Telegram user can hold a chat with two tenants' bots, and one unmute would clear both — so they are served by hand-written pages (`panel/views.py`, `/admin/users/`) that join all three into one row per chat and unmute on both key columns.
- **The panel does not drive the funnel.** `funnel.on_*` runs in the bot process; editing an order's status here moves the row without messaging the client, re-planning their scheduled touches, or telling Bitrix. Use the operator bot for that, and the panel to fix data.
- **The record is read-only.** `conversation_events` (the corpus the agents are debugged and trained from) and `maskan_payments` (state the providers assert) use `ReadOnlyAdmin`. `learning_examples` is editable because approving a pending example *is* the review workflow — but the pgvector `embedding` column is deliberately unmapped, and `scripts/gold_review.py` still computes it.
- **The interesting pages are not model admins, and they are organised around one number.** `crm/scoring.py` gives every chat a **buy probability** (0-100) as a sum of *named* signals — funnel stage (the only signal that is a commitment, so it carries most of the weight), messages sent, phone given, whether they answered our last message, decayed by how long they have been silent — and the categories on the customer list are buckets of that percentage rather than a separate taxonomy. Three properties are deliberate: it is **explainable** (every page can show the exact lines that produced the number, and the customer page does), **derived and never stored** (changing a weight re-scores all of history on the next page load), and computed from **behaviour, not words** (no sentiment, no model call). On top of it `panel/views.py` + `crm/analytics.py` build a home page that is a worklist ("talk to these people today", ranked), a **customer directory** (probability, category chips that double as the filter, messages in/out, CSV), a **customer page** that renders the conversation like the chat it mirrors plus a `t.me/…` link that opens it in Telegram, an **automatic-messages page** (`crm/outreach.py`: the pacing rules, the queue with cancel / +1 day / send-now, and what actually went out), and an analytics page (volume, revenue, funnel, touch mix, **per-tool failure rates** off the corpus). Charts are inline SVG rendered server-side by `panel/charts.py` — no CDN and no JS, because the panel runs on an internal host that may have no outbound network and a chart that silently fails to load is worse than a table.
- **The panel writes five things, and no more.** Un-muting a chat; the outreach rules (`panel_settings`, one JSON row per `(tenant_id, key)` — a generic key/value table because the panel is its only writer and a knob should be a form field, not a migration); the *timing* of a queued touch; a **«sotib olgan» mark** on a lead; and a **new operator-scheduled message** to one chat. It never edits a touch's text: the text is composed by the agent at send time in the client's own language, so there is nothing to edit until it exists.
- **«Sotib olgan» moves the category, never the money.** The button writes `maskan_leads.status = 'won'` (plus stage 5 and an audit note in `close_reason`) and cancels that chat's queued messages. It deliberately does **not** invent a paid order: an operator asserting a sale the system never saw — cash, a transfer, a deal closed by phone — is a fact about the relationship, and a fake order would put money nobody received into the revenue KPI. `crm/scoring.py` reads the status and shows 100%; revenue keeps coming from orders the payment providers confirmed. `status='won'` is safe for the runtime because `get_active_lead_by_chat` only excludes `closed`.
- **Three pages exist so the operator never needs SSH.** `/admin/prompts/` edits the agents' system prompts on disk (`crm/prompts.py`, a static registry mirroring `admin/prompts.py` — the browser sends a `(tenant, key)` pair and the path is resolved server-side, so the edit surface cannot escape the prompt directories). The bots re-read those files on every reply, so a save is live without a restart, and every save keeps the previous version under `prompts/.history/` because a bad prompt edit is the fastest way to break a working sales agent. `/admin/health/` (`crm/health.py`) answers "is it running, and is it working": the systemd units via `systemctl show` (an argv list, never a shell), whether a customer message is sitting unanswered, and a restart button for the bot units through `sudo -n`. `/admin/settings/` (`crm/env_settings.py`) edits a **fixed allow-list** of `.env` keys — the phone, the operator ids, the memorial dates — and never reads or writes anything else, because a merchant key rendered into a form is one screenshot from being someone else's; unlike the outreach rules these are folded into a frozen config at import, so the page says a restart is needed and links to the button.
- **The health page must not cry wolf.** A quiet day is a note, not an alarm; a unit somebody deliberately `disabled` shows as «o‘chirilgan», not as a failure; and the eval chat-id block is excluded from the task counts for the same reason every other page excludes it. What is left — a customer waiting on an answer, a unit that should be running and is not — is worth waking someone for.
- **A chat can hold more than one lead, and the newest one wins.** The funnel opens a fresh lead when a returning client writes after a closed deal, so `chat_rows` iterates `MaskanLead.objects.order_by("id")` and lets the last write stand — matching `set_state` and the runtime's `get_active_lead_by_chat`. Without the explicit ordering `Meta.ordering = ("-updated_at",)` leaves the *oldest* lead winning, and the panel shows a closed deal for a customer who is mid-conversation. The same class of bug bit `tenants()`: `.values_list(…).distinct()` under a model `Meta.ordering` distincts over `(value, id)` — one row per event — so it needs `.order_by()` first.
- **Eval chats are filtered out of every aggregate.** `scripts/eval_run.py` reserves a high chat-id block (`EVAL_CHAT_BASE`) and deletes its own rows; a crashed run leaves them, and one synthetic *paid* order makes the revenue KPI wrong. `crm/analytics.py::EVAL_CHAT_MIN` hides them, every page reports how many it hid and links to `?eval=1`, and the per-chat page ignores the filter so a link to an eval chat still opens. Never make the exclusion silent — the id window can in principle catch a real chat.
- **The panel is light, and bilingual.** `admin/base_site.html` empties Django's `dark-mode-vars` block — no dark stylesheet, no theme toggle — because the panel is read in daylight by people who never asked for a dark editor; `panel.css` then redefines the admin's own CSS variables onto one light palette so the stock model pages match. Django's header and breadcrumb bar are replaced by a single topbar for the same reason the pages were trimmed: two stacked navigation strips on every screen is what made this feel heavy. One CSS gotcha is worth knowing: Django underlines links with `a:not([role="button"], #header a, …)`, and `:not()` takes the specificity of its *most specific* argument, so that rule counts as an id and no class can outrank it — the panel's tables and buttons un-underline with a scoped `!important`.
- **Two languages, one dictionary.** `crm/i18n.py` is a plain `uz → en` table with a `{% t %}` tag and a `|t` filter, not gettext: the server has no `msgfmt`, so a `.po` could not be compiled there, and a build tool for two languages is a worse trade than a table anyone can edit. **Uzbek is the source language** — the key *is* the Uzbek string — so a phrase with no entry still renders correctly and merely stays Uzbek. Django's own strings switch through the catalogues it already ships, via `LocaleMiddleware` and the topbar's `set_language` form. A number that sits on a different side of its word in each language gets a filter instead of two strings (`|bosqich` → "4-bosqich" / "stage 4"); translating the halves separately is how you get "4 — stage".
- **Marking someone as bought arms one message a month out.** `crm/outreach.py::schedule_repeat` queues an `operator_repeat` task 30 days ahead — "shall we look after it this month too?" — because grave care is repeat work and a month later nobody remembers to ask. It rides as an *operator* message (`source: operator`), so it passes the "the bot never writes first" switch while still obeying quiet hours; its `dedup_key` is `op:repeat:<chat_id>`, which is unique, so marking a client bought twice moves the same row rather than queuing two. Taking the mark back cancels exactly that row and leaves anything scheduled by hand. The executor (`apps/maskan/funnel.py::_exec_operator_repeat`) has no script of its own beyond a directive and `msg.s8_month_later`: the text is composed at send time in the client's language, and the directive forbids quoting a price, because the catalogue is the only place a number may come from.
- **The category is derived, but two states are assertions.** The heat buckets are the score's estimate and cannot be hand-set — setting an estimate only makes it untrue. What a person knows and the system cannot see is that they bought or that the deal is dead, so `/admin/users/<…>/` offers exactly `faol / sotib olgan / yopilgan` (`crm/outreach.py::set_state`, writing `maskan_leads.status`). It writes *only* the status: bumping the stage too would make the change irreversible, since reverting could not know which stage to go back to.
- **`{# … #}` is single-line in Django templates.** A multi-line one renders as page copy. The panel's templates use `{% comment %}` throughout for that reason.

**Two distinct RAG strategies share `rag/VectorStore` (a ChromaDB wrapper):**
- **oygul** uses `CLIPEmbedder` (`clip-ViT-B-32`, multimodal): embeddings are computed *externally* and passed as vectors. **Catalog search queries must be in English** — CLIP's text encoder is English-trained, so the agent translates intent to English before searching. Bouquet prices are stored in **tiyin** (`price // 100 = sum`); see `apps/oygul/models.py`. The merchant `add_bouquet_tool` ingests live (the online equivalent of `scripts/oygul_embed.py`): the uploaded photo → **Cloudflare Images** (`apps/oygul/photos.py`, durable public URL) → CLIP embed + Chroma upsert (`BouquetSearch.index`) → a `oygul_bouquets` row via the repository. The merchant channel sets `retain_images=True` so a photo uploaded earlier in the chat is still reachable when the merchant later confirms "save" (per-chat accumulator published on `current_images`).
- **anfa** uses `LiteLLMEmbeddingFunction` (text embeddings) set as Chroma's `embedding_function`, so you pass *texts* and Chroma embeds. One collection holds two doc types — the priced service catalog (`service_*` docs — title + category + tab; price is metadata only) and the doctor roster (`doctor_*` docs — name + speciality + experience; walk-in hours in metadata); `apps/anfa/sync.py` refreshes both incrementally by content hash. Multilingual embeddings let Uzbek queries match the Russian-language catalog and the Uzbek roster.

**Model/provider config.** The chat model is built via langchain `init_chat_model` with `temperature=0`, provider-routed by `CHAT_PROVIDER`/`CHAT_MODEL` (default `groq` + `openai/gpt-oss-20b`). **OpenAI is always required regardless of chat provider** — voice transcription and embeddings go through OpenAI. A `SummarizationMiddleware` compresses history past ~10k tokens. `Agent.compose` (the proactive-message path) has its own system prompt and a `_plain_message` post-pass that strips the notification costume — emoji, `**bold**`, bullet lists, separator rules, `Eslatma:`/`Reminder:` labels — because an unprompted message is the one most at risk of reading like an SMS blast rather than like the person the customer was already talking to. A tenant may pass a *callable* `system_prompt` that is re-rendered every invoke (anfa injects the current clinic-timezone datetime); the agent graph is rebuilt only when the rendered prompt changes.

**Meta channels are handlers, not transports (`channels/meta/`).** Telegram dials out and long-polls; Meta calls *us*, so a WhatsApp/Instagram/Messenger channel has nothing of its own to run. `webhook.MetaWebhookServer` is the part that runs — one ASGI app on one URL, because Meta gives an app a single webhook and tags every product's events by `object` — and each channel registers a handler into it; whichever channel `Runtime` starts first serves the port and the rest await the same future. It runs **inside the bot process** (unlike `payments_api.py`, which only writes a row): an inbound message has to reach a live `Agent` with its checkpointer and mute store, and in-process makes that a function call instead of a queue. `fastapi`/`uvicorn` are therefore **base dependencies**, not an extra — two runtime pieces need them in a deploy that installs no extras.
- **The signature is mandatory and the endpoint fails closed.** A POST here is indistinguishable from a real customer writing, so forged traffic would spend money and poison the corpus. Without a valid `X-Hub-Signature-256` the request is refused, and with no app secret configured *every* POST is refused with 503 — the channel does not even start (`config.whatsapp_configured` requires the secret), because an endpoint that cannot tell Meta from a stranger is worse than no endpoint.
- **The chat id is the phone number.** WhatsApp's `wa_id` is digits with no `+`, which fits the `BigInteger` `chat_id` every table already uses — no id-mapping table, and the panel keys on it unchanged. `thread_id` is `tenant:whatsapp:<wa_id>`, so the same customer on Telegram and WhatsApp holds two separate conversations, which is correct: they are two different people as far as identity goes.
- **A human can take a conversation over, on either transport.** On Telegram they simply type from the bot's own account: `capture_operator_messages` notices the outgoing message, mutes the chat and files it under the `operator` role. WhatsApp has no account to type from — the number is API-only — so the panel's customer page carries a reply box instead. It cannot call the channel (different process, and the panel imports none of the bot runtime), so it queues an `operator_message` task and the scheduler delivers it on the next tick; the executor sends the text **verbatim** (an operator who typed a sentence meant that sentence), mutes the chat, and records it as `operator` so the agent has the human's side on handback and the learning loop can harvest it. The scheduler polls every 15s (`MASKAN_SCHEDULER_INTERVAL_SECONDS`) rather than the old 60 — a reply typed into a live conversation should not sit for a minute, and the poll is two indexed queries against a small table. `IMMEDIATE_ACTIONS` exempts it from the pacing gate: quiet hours exist to stop the funnel pestering people, and holding a human's own reply until 09:00 would be absurd. The panel checks the 24-hour window *before* the operator types and shows why the box is unavailable, because discovering that after pressing send is the wrong moment.
- **Outside WhatsApp's window a touch becomes a template, or fails loudly.** `Channel.freeform_allowed(chat_id)` is True everywhere except WhatsApp, which measures 24 hours from the customer's last message (`db/outreach.py::last_inbound_at`; no record at all counts as *outside*, since Meta would refuse anyway). The funnel asks **before** composing — a model call that produces an undeliverable message is money for nothing — and on a shut window sends the `Template` the touch names (`funnel.TEMPLATES`, mapping an action to an approved template). With no template, or if Meta refuses it, `_send_client_directed` **raises**: the scheduler parks the task as failed and the panel shows it. Dropping it quietly is the outcome to avoid. One asymmetry catches everyone building this: Meta's *sample* for a dynamic URL button is a whole URL, but at send time only the part after the fixed base is passed.
- **A touch is delivered on the transport that chat used.** `FunnelContext.customer_channels` holds every client-facing channel and `funnel._channel_for(chat_id)` picks between them from the corpus's `channel` column (one indexed lookup, nothing next to the model call that follows). This is not a nicety: a Telegram id and a WhatsApp phone number are different address spaces, so delivering to the wrong one does not fail loudly — it writes to a stranger, or to nobody. The panel's contact link is channel-aware for the same reason (`ChatRow.contact_url` → `wa.me/<number>` or `t.me/<username>`).
- **The 24-hour window is the one rule Telegram does not have.** Outside 24 hours from the customer's last message Meta refuses free-form text and only an approved template may be sent; `WhatsAppChannel._post` names error 131047 explicitly rather than logging a generic failure, because a scheduled touch failing silently is exactly what this subsystem exists to prevent.

**The notifier bot is the channel bot.** `notifications/operator.py` fans out to operators over the raw Telegram Bot HTTP API (httpx), while the same bot token's Telethon client (the merchant/bot channel) listens for the unmute button's callbacks. `UNMUTE_CALLBACK_PREFIX` (`unmute:<chat_id>`) is the shared contract between them.

## Config conventions

- Each tenant has a frozen `config.py` dataclass instantiated at import (`config = OygulConfig()`), with `load_dotenv()` called first. Fields resolve **tenant-prefixed env first, then a shared fallback** (e.g. `OYGUL_TG_API_ID` → `TG_API_ID`).
- Entrypoints inject the resolved OpenAI/Groq key into `os.environ` so the litellm/openai SDKs pick it up.
- Per-tenant services in `services.py` are lazy module-level singletons (`get_voice()`, `get_notifier()`, …); tests/overrides monkey-patch those slots.
- `anfa` keeps two Postgres tables in `apps/anfa/models.py` (+ `repository.py`), both fed by clinic exports and reconciled whole on each import (stable ids, so re-imports are incremental): a **flat service catalog** `anfa_catalog` (from the clinic's `.xlsx` — `tab` Прием/Лаборатория/Услуги/Диагностика/Операционный/Группа, `category` speciality-for-Прием, `title`, `price` UZS; parsed by `import_catalog.py`, id = `sha1(tab|category|title)`) and a **doctor roster** `anfa_doctors` (from a `.docx` — name, speciality, experience, weekly `schedule` + a clean `hours_label`; parsed by `import_doctors.py`, id = `sha1(fullname)`). Both are *reference* data — there is no visit/availability data and **no online booking**; the clinic registers patients in person and the roster's hours are shown as walk-in times. Each import runs two ways: an admin-panel upload (`has_catalog_import` / `has_doctors`) and a CLI (`scripts/anfa_import_catalog.py`, `scripts/anfa_import_doctors.py`). The catalog agent's tools (`apps/anfa/tools.py`, `CATALOG_TOOLS`) are `search_services` (→ priced results), `search_doctors` (→ name + experience + walk-in hours), `list_service_categories`, `request_operator` (notifies staff, keeps answering), and `handoff_for_results` — the one true handoff, used *only* when the client wants their lab/analysis results: it notifies moderators with the "Подключить ИИ" button AND mutes the chat so a human sends the results (re-using oygul's callback infra). It needs the client's full name + date of birth for the lab desk to find them; clients often supply both by **sending a photo of their passport**, which the agent reads off the image (see "PHOTOS THE CLIENT SENDS" in `prompts/catalog_system.md` — the prompt must explicitly authorise this or the model refuses ID documents on reflex). Emergency triage (`apps/anfa/triage.py`) still runs as a deterministic `message_guard` before the agent. A short KB sync interval (`ANFA_SYNC_INTERVAL_SECONDS`, default 300s) mirrors both tables into Chroma quickly.
- Telethon is pinned exactly (`telethon==1.43.2`). Sessions live in `data/*.session` (gitignored); a user-account channel fails fast if its session isn't pre-authorized (run the login script once). `mark_read` is silently skipped on bot accounts (Telegram forbids it).

**The durable scheduled-task queue (byd + maskan).** Both funnel tenants run the same engine, and it is the piece to copy for any tenant that needs time-delayed outreach. A `<tenant>_scheduled_tasks` table holds "run `action_type` for lead L at time T" rows; a `SyncJob` poller claims due rows with `FOR UPDATE SKIP LOCKED` (so two processes never double-fire), dispatches each through the funnel's `ACTIONS` registry, and marks it done or retries it with backoff before parking it in `failed`. Enqueue is idempotent via a deterministic `dedup_key`, and `ON CONFLICT` **resets** the row rather than doing nothing — that is what lets a transition cancel-then-re-enqueue a plan, and what lets a chat-silence timer be pushed back by each new inbound message. `reclaim_stale_running` un-sticks rows left by a crashed poller. Executors run out-of-band with **no** `current_channel`/`current_chat_id` context vars set — they reach the live channel and notifier through the funnel's `get_context()`, wired once at startup by the entrypoint. Scheduled touches deliberately bypass the mute gate (`compose_outbound` + `send_text`, not `dispatch`): they are pre-scripted funnel steps, not the AI conversing, so a human operator owning the chat still gets their CRM reminders sent. Each touch is composed **through the agent** (`compose_outbound`) so it lands in the customer's own language, with a verbatim `fallback` template and `must_include` fragments (payment links, addresses) re-appended if the model dropped them; a fallback send is logged to the corpus by `db/outreach.py::log_sent_touch`, since only the composer logs itself.

**The outreach pacing gate (`db/outreach.py`).** The last thing between a due task and a Telegram send, and the reason the funnel does not read as a notification service. `execute_task` calls `check_send(tenant, chat_id, tz)` for every *client-facing* action (staff/SLA/`bitrix_*` actions are exempt — an operator's own reminder is not marketing) and gets back either "send" or "not now, retry at T"; on the latter the row is put back via `repository.defer_task`, which also rolls back the claim's `attempts` increment so a deferral can never push a task toward `failed`. That is why `execute_task` returns a **bool** and the scheduler only calls `mark_task_done` when it is True. The rules are read live from `panel_settings` through `db/settings.py` (20s TTL cache, so a switch flipped in the panel reaches the running scheduler in seconds).

**`enabled` is off by default — the bot never writes first** (the owner's decision, 2026-09-04: the messages that survived the old drip said nothing the client needed, and a funnel that chases people reads as a spam service). With it off, a funnel-initiated touch is **cancelled**, not deferred: the switch stays off indefinitely, so a deferral would just park the row in the queue forever. That is why `Decision` carries a `drop` flag and the repositories have both `defer_task` and `cancel_task`.

**What still goes out.** Staff-facing tasks (SLA, `bitrix_*`) are exempt from the gate entirely. Transactional messages are not scheduled tasks at all — a payment confirmation or the finished-work photos are reactions to something that happened, not a chase, and they still send. And a touch whose payload carries `source: "operator"` (`db/outreach.py::is_operator_task`) is let through the switch: "the bot must not chase people" is a rule about the funnel's initiative, not a gag on the person running it. Those are queued by the panel's customer page (`operator_followup`, whose executor has no script — the operator's note says what to raise and the agent writes it at send time). Quiet hours still apply to them; the daily cap and minimum gap do not, since one deliberate act is not a drip.

When the switch *is* on, the remaining rules pace the drip: a quiet-hours window, a per-chat daily cap and a minimum gap, with the cap counting `conversation_events` rows of `role="outbound"` — what the client actually received. Everything fails **open**: an unreadable policy sends, because a database hiccup silencing the funnel is worse than one message landing out of its window.

**Maskan payments go to the operator's own merchant account.** The Django backend can mint a Payme link, but that link pays *Maskan's* merchant. This tenant sells for the operator running the bot, so `create_order` opens its own invoice (`maskan_payments`, one row per order, amounts in **tiyin**) and returns a link per configured provider — Payme (base64 `m=…;ac.<field>=<invoice>;a=<tiyin>`) and Uzum Bank (a `serviceId` deeplink). With no merchant credentials set it silently falls back to the backend's link, so a half-configured deploy still sells. Three pieces, deliberately split across processes:
- **`payments_api.py` is its own web process** (`maskan-payments-api`, behind nginx+TLS — see `deploy/maskan-payments.nginx.conf`). It speaks Payme's Merchant API (JSON-RPC: CheckPerform → Create → Perform, plus Cancel/Check/GetStatement, `Basic base64("Paycom:<key>")`) and Uzum's check/create/confirm/reverse. It only moves the invoice's state — it has no Telethon client and sends nothing.
- **`payment_watcher.py` does the talking**, inside the bot process. It claims paid-but-unnotified invoices (`claim_paid_payments` stamps `notified_at` under FOR UPDATE SKIP LOCKED, so the client is thanked exactly once) and runs the ordinary `funnel.on_payment_received`. A failure un-stamps the row so the next tick retries.
- **The backend still doesn't know.** Money landing in *our* merchant account never reaches Maskan's `payment_status`, so the caretaker dispatch that the backend does on payment does not fire — an operator closes that loop by hand today. Adding a `mark-paid` botapi endpoint is the automation, and it is a Django change.

Note `from __future__ import annotations` + FastAPI: handler type hints are resolved against **module** globals, so `Request`/`Header` must be imported at module scope — imported inside the factory, every body parameter silently degrades to a query parameter.

**The conversation corpus (`conversation_events`).** Every turn every agent handles is appended to one shared, tenant-scoped, append-only table by `db/training.py`: the customer's message, each tool call with its arguments and a computed `ok` flag, the reply (with tokens/latency/model), the composed out-of-band funnel touches, and — the part that makes it *trainable* — the funnel outcome, logged from `apps/maskan/repository.py` on every stage/status change. Rows of one turn share a `turn_id`, a whole dialogue shares `thread_id`, so `scripts/export_training_data.py` can rebuild each conversation in order and attach its outcome label (`--stats` to inspect, `--out x.jsonl` to export). Three things to keep in mind before editing it:
- **It is deliberately not the checkpointer.** LangGraph checkpoints are the agent's *working* state — summarised past ~10k tokens, compacted, overwritten — so they can't answer "what did the customer actually type in July". This table is the immutable record; the checkpointer stays the runtime state.
- **Writes are best-effort and must stay that way.** `db/training.py` swallows every exception and `Agent._log_turn` wraps it again: a logging failure must never cost a customer their reply. Collection is on whenever `DATABASE_URL` is set; `TRAINING_LOG=0` turns it off.
- **The `ok` flag on tool rows is the point.** It recognises all three failure shapes (LangChain `status="error"`, a bare `error: …` string, and the tenants' `{"success": false, …}` convention from `apps/*/tools.py::_fail`), which is what makes "which tool is failing in production, and what did the agent say when it did" a one-query question.

**The learning loop (`core/learning/` + `db/training.py`).** The corpus described above is the input; this is what reads it. Three pieces, and the order matters — each one is useless without the one before it.
- **Evidence.** Every assistant row carries `prompt_version`, a hash of the *authored* prompt (digits stripped, so a tenant injecting the clock does not churn it). Prompts are edited live with no restart, so a hand-kept version number would drift; hashing is exact and makes "did that edit help?" a group-by. `scripts/corpus_report.py` is the weekly read: funnel drop-off, per-tool failure rates with real error strings, and `call_human` reasons grouped by a normalised key — that last list *is* the defect backlog, since every handoff is a thing the agent could not do.
- **A scoreboard.** `core/learning/evals.py` + `apps/<tenant>/evals/cases.jsonl` + `scripts/eval_run.py`. A case is a scripted conversation plus assertions about *behaviour*, never wording: which tools were called, whether every four-plus-figure number said aloud exists in the catalogue (years excluded by range), whether an order was opened without a clear yes, which script the reply used. Deliberately **no LLM judge** in this layer — these checks are exact and free, which is what makes them safe to gate a deploy on. Each case runs in a reserved chat id under tenant `<tenant>-eval`, reads its tool trace back out of `conversation_events` (so the evals exercise the real logging path), and deletes its own leads/orders/graves afterwards — an eval that leaves a fake lead behind sets the scheduler writing to a chat that does not exist.
- **The one loop that changes behaviour by itself.** A human's reply after a handoff is the answer the agent should have given, and it used to exist only in the LangGraph checkpoint, which is summarised and overwritten. `record_user_message(..., log_role="operator")` now files it in the corpus; `scripts/gold_review.py --harvest` (daily timer) turns those into pending rows in `learning_examples`; a person approves them; `Agent._examples_for` retrieves the approved ones per message (pgvector when `EMBED_MODEL` is set, `pg_trgm` similarity otherwise) and appends them to the prompt. **Money is masked to `{narx}` on the way in** — an example may only ever teach phrasing, never a price, which still comes from the catalogue on every quote. Retrieval is per-message state on an Agent shared by every chat, so the block is applied under a lock and the caller keeps a *local* reference to the graph it built; a concurrent turn rebuilding `self._graph` cannot swap another chat's examples into this call.

**Staying alive (`scripts/watchdog.py`, `deploy/`).** A systemd timer runs the watchdog every 5 minutes outside the bot process — the failure it most needs to report is that process being dead. It checks the unit, Postgres, that conversation logging is on and writing, that the operator bot can actually *reach* an operator (a valid token whose admin never pressed Start delivers nothing — this deployment's real failure mode), disk, and backup freshness. Only state *transitions* alert, so a long outage does not spam and a recovery is announced once; if the alert itself cannot be delivered the transition is not recorded, so the next tick retries instead of going quiet forever. `OnFailure=ai-agent-alert@%N.service` on each unit fires the same alert the moment systemd sees a crash. `deploy/ai-sales-backup.sh` (nightly timer) dumps the database plus a corpus-only dump kept far longer, and fails loudly on an empty file — a zero-byte backup is worse than none.

**Maskan is standalone: it owns its catalogue and its money.** It used to be the reference for "a tenant whose domain data lives in someone else's system" — the Flutter app's Django backend owned the prices, graves, orders and payments, and `api_client.py` reached them over HTTP. That is no longer the sales path. `apps/maskan/models.py` now holds `maskan_services`, `maskan_cemeteries`, `maskan_graves` and `maskan_orders` alongside the funnel state, and the tools read and write only those. Four things follow:
- **No client account, anywhere.** The Telegram chat id *is* the identity — no app, no password, no phone linking. (The old flow needed a Maskan account, and the security note still stands for anyone tempted to re-add it: `telegram_chat_id` is where password-reset codes go, so a "link by phone number" tool would be an account-takeover hole. Don't build one.)
- **Prices are still not the model's to invent.** `list_services` reads `maskan_services` on every quote, and an order stores a *snapshot* of what was sold (`items`: code, name, price at the time), so a later price edit cannot change what a client already agreed to pay. Seed/edit the catalogue with `scripts/maskan_seed_catalog.py` (reconciles by service `code` / cemetery `name_uz`; CSV import supported).
- **The cemetery table is the service-area rule.** Only Tashkent city and Tashkent region are in it, so a cemetery outside the caretakers' reach cannot be quoted for — `find_cemetery` returns `out_of_area` instead of a price.
- **Work status is set by staff, not observed.** There is no `OrderWatcher` any more: after payment, an operator moves the order with the manager tools `open_orders` → `order_accepted` → `order_completed`, each of which runs the matching `funnel.on_*` transition. Payment itself is still never asserted by a tool — see the payments section above.
- Seasonal demand is the real driver: in Uzbekistan graves are visited before Hayit and on Arafa. Those dates are lunar, so `MASKAN_MEMORIAL_DATES` is an admin-maintained ISO date list and the funnel schedules a nudge `MASKAN_MEMORIAL_LEAD_DAYS` before each. The `memorial` action is deliberately **stage-independent** (`_STAGE_INDEPENDENT` in `funnel.py`) — it survives stage transitions, since a client who just paid and a client who went cold both want it.

## Adding a tenant

1. Create `apps/<tenant>/` with `config.py` (env-driven dataclass), `tools.py` (`@tool` functions), `services.py` (singletons + the JSON/Postgres store switch), and `prompts/`.
2. Write an entrypoint that builds `Agent`(s), binds them to `Channel`(s), assembles a `Tenant`, and runs it inside `async with checkpointer_scope() as cp: await Runtime(build_tenant(checkpointer=cp)).run_async()`.
3. Register console script(s) in `pyproject.toml [project.scripts]` and add a pm2 app in `ecosystem.config.js`.
4. If the tenant should show up in the admin panel, add it to `TENANTS` in `admin/tenants.py` (id, display name, channel names).

**Per-tenant domain data (CRM) lives in the tenant, not in `db/` or `admin/`.** A tenant that persists its own domain data (catalogue, orders, bookings) owns two files: `apps/<tenant>/models.py` (SQLAlchemy ORM tables, declared on the *shared* `db.models.Base`) and `apps/<tenant>/repository.py` (all DB reads/writes for that tenant). The same repository serves both the bot write path (tools) and the admin read/manage path. Keep `models.py`/`repository.py` import-light — only `sqlalchemy` + `db.engine` + the tenant's own `models` — so the admin panel can import the repository without dragging in CLIP/telethon/langchain. `db/models.py` stays tenant-agnostic (shared `Base` + `muted_chats`/`chat_token_usage` only). Two wiring steps: declare tables on `db.models.Base`, and `import apps.<tenant>.models` in `db/migrations/env.py` so `alembic revision --autogenerate` sees them. (oygul is the reference implementation: `oygul_bouquets` + `oygul_orders`, migration `0002`.)
